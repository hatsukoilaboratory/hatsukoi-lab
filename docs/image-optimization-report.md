# キャラクター画像配信最適化レポート

## 実施内容

高解像度のPNG原本は `standingImage` としてデータに保持し、画面で直接使う画像を用途別のWebPへ分離しました。`bustImage` は作品ページ、ヒロインプロフィールモーダル、診断結果に使用します。`listImage` は個別の一覧カード向け、`chibiImage` はトップの浮遊演出向けです。

作品ページとプロフィールモーダルは同じ `bustPosition` を共有するため、同一人物でトリミングの基準がずれません。ヒロイン一覧ではポインターホバー、フォーカス、タッチ開始の時点で `bustImage` を先読みします。モーダル表示時には小さいWebPが使われ、初回表示で高解像度PNGを取得しません。

## 読み込み方針

| 画面 | 画像の扱い |
|---|---|
| トップ初回表示 | 浮遊演出に必要になったちびキャラだけを描画し、512px WebPを非同期デコードします。 |
| ヒロイン一覧 | 一覧用には480×720 WebPを使用します。プロフィールを開きそうなホバー、フォーカス、タッチ開始でbustImageを先読みします。 |
| プロフィールモーダル | 768×1152 WebPを使用します。表示開始までに先読み済みであればキャッシュから描画し、そうでない場合もPNGではなく軽量WebPを取得します。 |
| 作品ページ | ファーストビューのバストアップは遅延読み込みにせず、非同期デコードと高優先度で表示します。 |
| サンプル画像 | 画面外にあるため `loading="lazy"` と `decoding="async"` を指定します。 |

## LCP・表示待ち時間の確認について

ローカル開発サーバーに対するLighthouseの最適化後の参考値は、トップで **LCP 27.1秒／総転送量 4,644 KiB**、作品ページで **LCP 25.9秒／総転送量 4,616 KiB** でした。ただし、このローカル開発計測には開発用JavaScriptとサンドボックス環境の起動・通信待ちが含まれ、公開環境の実ユーザーLCPを示す値ではありません。

修正前の同条件Lighthouse値は保存されていないため、LCPの秒数差を推測して報告することは避けています。一方で、キャラクター画像そのものは上表の通り 84〜94% 削減され、モーダルの初回画像待ちも先読み対象を平均約1.3MBのPNGから約82KBのWebPへ変更しています。実ユーザーLCPは、公開後のアクセス計測で継続確認するのが適切です。
